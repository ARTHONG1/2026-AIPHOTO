# 사진을 서버에 보관하지 않는 QR 전달

## 동작
- 촬영 원본·AI 결과·프레임 사진은 부스 탭 메모리에만 둔다. sessionStorage/localStorage/DB/Cloud Storage에 사진을 쓰지 않는다.
- QR에는 `/receive/방번호#수신토큰`만 담는다. 토큰은 URL fragment라 HTTP URL 및 Referer로 전송되지 않는다.
- `/api/transfer`는 사진을 받지 않고, 최대 32KB의 인증된 WebRTC 연결 정보만 RAM에 둔다.
- 사진은 암호화된 WebRTC DataChannel로 전달한다. 16KB 단위 전송, 버퍼 제한, 크기 제한, SHA-256 및 이미지 디코딩 확인 후 수신 완료를 알린다.
- 첫 화면 복귀·다시 고르기·프레임 변경·페이지 종료 때 전송을 취소하고 방을 폐기한다. 서버 요청이 실패해도 PC 연결은 즉시 닫고, 방 정보는 PC heartbeat 중단 후 3분 이내 자동 만료한다.
- 사진을 받는 중에는 60초 자동 초기화를 멈춘다. 연결·전송은 최대 90초 후 오류 안내를 한다.
- 받은 사진은 휴대폰의 Blob URL로 라이브 효과·스티커·AR·다운로드·사진 파일 공유를 실행한다. 사진을 앱이 자동 영구 저장하지 않는다. 사용자가 사진 저장을 눌러야 한다.
- 새로고침하면 메모리 사진은 사라진다. `/receive`에서 저장한 사진을 다시 선택해 AR을 실행한다. 이 경우 이전 배경 선택은 알 수 없어 기본 AR 배경으로 시작한다.

## 행사 운영 조건
- PC와 휴대폰 모두 같은 배포본의 외부 접속 가능한 **HTTPS** 주소를 열어야 한다. `127.0.0.1`은 PC 전용 미리보기이며 휴대폰에서 PC를 가리키지 않는다.
- 기본 STUN만으로 모든 Wi-Fi/LTE/방화벽 연결을 보장할 수 없다. 행사 운영 전 TURN 서버의 `PHOTOBOOTH_TURN_URLS`, `PHOTOBOOTH_TURN_USERNAME`, `PHOTOBOOTH_TURN_CREDENTIAL`을 호스팅 환경 변수/Secret Manager에 설정하고 실제 iPhone·Android에서 테스트한다. TURN은 암호화된 패킷을 중계하며 사진 보관 기능은 구현하지 않는다. 공급자의 로그·보관 정책은 별도 확인한다.
- 연결 정보 저장소는 **한 개의 상시 Node 프로세스**를 전제로 한다. 기존 App Hosting maxInstances=1은 유지한다. 여러 인스턴스·여러 Node worker·롤링 배포·컨테이너 재시작에서는 방이 사라질 수 있다. 여러 프로세스로 운영하려면 사진을 저장하지 않는 별도 단일 signaling 서비스를 두어야 한다. 사용자에게 만료 안내와 QR 재발급을 제공한다.
- 부스 PC가 결과 화면을 떠나면 기존 QR로 사진을 다시 받을 수 없다. 수신 완료된 휴대폰의 AR은 PC 초기화와 독립적으로 작동한다.

## 범위
기존 QR 업로드 action, Cloud Storage 업로드 코드 및 사진 프록시는 제거/폐기했다. 과거에 업로드된 Cloud Storage 객체를 원격 삭제하는 작업은 하지 않았다.
Vertex AI 합성은 유지한다. 합성을 실행하면 사진이 Google에 전송되며, 서버 저장 제거가 외부 AI 전송 또는 아동 이용 약관 문제를 해결하지 않는다.
메모리 참조를 정리하는 것이며 운영체제 스왑·브라우저 메모리의 물리적 덮어쓰기를 보장하지 않는다. 사용자가 직접 저장·인쇄한 파일은 삭제하지 않는다.

## 검증
`node --import tsx --test tests/transfer.test.ts`
`npm run typecheck`
`node tests/run-transfer-browser.cjs`는 설치된 Chrome과 Playwright 드라이버로 브라우저 두 컨텍스트에서 실제 DataChannel 전송, 전송 중 초기화, 만료 QR, 휴대폰 로컬 사진 선택 및 AR 권한 거부 화면을 확인한다. 기본 주소는 3012이며 `PHOTOBOOTH_TEST_ORIGIN`으로 다른 검증 서버를 지정할 수 있다. `PLAYWRIGHT_DRIVER`로 드라이버 경로를 바꿀 수 있다. 합성 테스트는 가상 사진과 mock 응답만 사용하며 실제 AI API를 호출하지 않는다.

실제 iPhone/Android 카메라의 AR 추적 및 Wi-Fi↔LTE 전달은 현장 장비·TURN 설정 후 별도 검증해야 한다.

## Magic Tree QR
- QR 연결 주소와 WebRTC 전송 방식은 그대로 유지한다. QR 화면은 [Magic Tree](https://github.com/Slifronic/magic-tree)(MIT)의 장면 코드를 `src/lib/magic-tree/`로 옮겨 쓴다. 수신 주소로 나무 모양을 정하고, 나무가 서 있는 바닥 판이 곧 QR이다.
- 처음에는 대각선 시점의 나무를 계속 보여 준다. 화면 또는 `QR 코드 보기`를 누르면 0.95초 동안 잎이 QR의 검은 칸으로 내려앉고 카메라가 위에서 내려다보는 시점으로 바뀐다. 이 렌더링 화면이 그대로 스캔용 QR이며, 다시 누르면 나무로 돌아간다. 모드 전환으로 방을 다시 만들지 않는다.
- 원본과 다른 점은 세 가지다. 결과 패널에 맞춰 하단 조작판 여백을 없앴다. 긴 수신 주소에서도 칸을 크게 유지하도록 오류 정정 단계를 원본의 H 대신 평면 QR과 같은 M(49×49칸)으로 쓴다. 화면 밖·백그라운드·정지한 QR 화면에서는 그리기를 멈춘다.
- Three.js는 결과 화면에서 미리 불러오며 준비 중에는 평면 QR 이미지를 보여 준다. WebGL 불가·컨텍스트 손실·렌더링 오류에는 평면 QR을 유지하며 `3D 다시 시도`로 새 캔버스에서 재시도할 수 있다. QR 생성 시 해당 영역으로 스크롤하며 페이지 종료·QR 재생성 때 GPU 리소스와 컨텍스트를 해제한다.
- 부스 QR 테두리는 연결·전송·수신 완료 상태에 따라 색이 바뀐다. 휴대폰 고리는 실제 수신 바이트의 진행률을 표시하고, 파일 검증과 이미지 디코딩이 끝나면 도착 표시로 전환한다.
- `npm run test:qr-portal`: 합성 사진과 모의 AI 응답으로 나무 기본 표시(동작 줄이기 포함), 잎이 내려앉는 중간 상태, 클릭·Enter·Space 왕복, 전환 도중 되돌리기, PC/390px에서 렌더링된 나무 QR 해독(원본 크기와 60% 축소+흐림), 크기 변경, 그래픽 장애와 재시도, 반복 전환, WebRTC 수신·다운로드 및 수신 완료 후 나무 복귀를 확인한다. QR 해독 라이브러리 jsQR은 개발 검증에만 사용한다.

### 2026-10-04 검증 결과
- 전송 단위 테스트 9개, TypeScript 검사, 격리 복사본의 프로덕션 빌드 통과.
- Next API 경로별 번들에서 오류 클래스가 달라 만료된 방이 500으로 처리되던 문제를 수정했다. 독립적으로 로드한 모듈로 재현 테스트를 추가했고 프로덕션 HTTP 410 안내를 확인했다.
- 느린 스크립트 로딩 중 사진을 먼저 선택하면 이벤트가 유실되던 문제를 수정했다. 화면 준비 전 사진 입력을 비활성화하고, 스크립트를 보류한 브라우저 검증을 추가했다.
- 프로덕션 서버에서 브라우저 두 컨텍스트의 실제 DataChannel 전송·수신 확인·사진 다운로드·PC 초기화 후 휴대폰 유지·만료 QR·스티커·로컬 사진 재열기·AR 카메라 권한 거부·전송 중 초기화 통과. 가상 사진과 모의 AI 응답을 사용했다.
- 검증 중 사진이 signaling 요청에 포함되거나 기존 사진 저장소/프록시로 전송되는 요청은 없었다. Playwright CLI로 사진 선택 화면과 스크린샷을 확인했고, 수신 진입 화면의 Chrome DevTools 콘솔 오류·경고는 없었다.
- 최종 Firebase App Hosting 배포본에서도 같은 브라우저 검증을 통과했다. 배포 환경의 TURN 설정은 비어 있다(`hasTurn=false`). 실제 휴대폰 간 Wi-Fi↔LTE 전달은 TURN 설정 후 현장에서 확인한다.
